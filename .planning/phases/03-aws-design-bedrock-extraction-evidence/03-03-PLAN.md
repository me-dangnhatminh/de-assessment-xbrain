# Plan 03-03: Live Bedrock Trial Execution and Evidence Capture

## Objective

Execute the five fixed Bedrock extraction cases against a real Amazon Bedrock endpoint, capture and commit all raw response evidence (with non-secret metadata), produce the field-level expected-vs-actual comparison report and trial summary, write honest observations about model behavior, and verify that the deterministic re-report command reproduces the summary without new API calls. This plan requires live AWS credentials and a Bedrock-enabled account with an accessible Converse-compatible model configured in `.env`.

**Prerequisites (must be satisfied before starting):**
- Plan 03-02 is complete: `design/` package exists, tests pass, `.env.example` is committed
- A `.env` file (gitignored) exists at repo root with valid `AWS_REGION`, `BEDROCK_MODEL_ID`, `BEDROCK_MAX_TOKENS`, and `BEDROCK_TEMPERATURE` values
- The configured model supports the Converse API (see RESEARCH §2.3 for compatible models)
- IAM permissions include `bedrock:InvokeModel` for the configured model and region

- .planning/phases/03-aws-design-bedrock-extraction-evidence/03-CONTEXT.md §D-11, D-12 (preflight requirements, model configurability)

<action>
Step 1 — Verify `.env` configuration:
Confirm `.env` file exists with non-empty `AWS_REGION` and `BEDROCK_MODEL_ID`. The model ID must be one that supports the Converse API (see compatible models list in RESEARCH §2.3 — all Anthropic Claude 3.x / Nova Micro / Nova Lite / Llama 3 Instruct family are confirmed). If an ARN-format cross-region inference profile is used (e.g., `us.anthropic.claude-3-haiku-20240307-v1:0`), that is valid.

Step 2 — Run the preflight command:
```bash
uv run --locked python -m design.bedrock preflight
```
This writes `design/output/preflight_result.json`. Expected pass output:
```json
{
  "status": "pass",
  "model_id": "<configured model>",
  "region": "<configured region>",
  "boto3_version": "1.43.68",
  "timestamp_utc": "2026-08-12T..."
}
```
If the preflight fails, diagnose using the `check` and `error_code` fields in the output JSON:
- `check: "credentials"` → AWS credentials not found; configure `AWS_PROFILE` or set access key env vars in `.env`
- `check: "iam_permissions"` → IAM role lacks `bedrock:InvokeModel`; add the permission
- `check: "model_not_found"` → model ID not available in the configured region; try a different region or model
- `check: "converse_not_supported"` → model does not support Converse; choose a different model ID from the compatible list

Step 3 — Commit the preflight result:
The `design/output/preflight_result.json` file contains ONLY non-secret metadata (model ID, region, boto3 version, timestamp). Verify it contains NO credentials, session tokens, or account identifiers before committing. Commit with message: `feat(phase3): add Bedrock preflight pass result`.
</action>

<acceptance_criteria>

### Task 2: Run the five-case Bedrock trial

<read_first>
- design/bedrock.py (cmd_trial — must check preflight gate, run all 5 cases, save raw responses)
- design/cases.py (CASES tuple — 5 fixed test cases: tc01–tc05)
- design/extraction_prompt.md (the prompt text to use — role, rules, output contract)
- design/output/preflight_result.json (must exist and have status:pass before trial runs)
- .planning/phases/03-aws-design-bedrock-extraction-evidence/03-CONTEXT.md §D-13, D-14 (raw response storage, non-secret metadata requirements)
- .planning/phases/03-aws-design-bedrock-extraction-evidence/03-RESEARCH.md §3.4 (expected outputs for each case — reference for expected-vs-actual comparison)
</read_first>

<action>
Step 1 — Run the trial command:
```bash
uv run --locked python -m design.bedrock trial
```
The trial command runs all 5 cases sequentially. For each case, it:
- Sends one Converse request using the configured model
- Saves the raw response + metadata to `design/output/responses/{case_id}_raw.json`
- Attempts JSON parsing of the model output
- Validates against the extraction schema
- Produces expected-vs-actual field comparison

Step 2 — Verify raw response files were created:
All five files must exist:
- `design/output/responses/tc01_raw.json`
- `design/output/responses/tc02_raw.json`
- `design/output/responses/tc03_raw.json`
- `design/output/responses/tc04_raw.json`
- `design/output/responses/tc05_raw.json`

Each file contains: `case_id`, `message`, `raw_response` (full Converse response dict), and `metadata` (non-secret invocation data: model_id, region, boto3_version, prompt_sha256, request_timestamp_utc, response_latency_ms, input_tokens, output_tokens, stop_reason, temperature, max_tokens).

Step 3 — Inspect raw responses for credential leakage:
Before committing, grep each file for: `SECRET`, `TOKEN`, `AKID`, `credential`, and any 12-digit numeric string that could be an account ID. The raw Converse response body contains only model output and usage metadata — no secrets should be present.

Step 4 — Force-add and commit raw responses:
The `design/output/responses/` directory is gitignored by default. After verifying no secrets, commit the evidence files using:
```bash
git add -f design/output/responses/
git add design/output/trial_summary.md
git commit -m "feat(phase3): add Bedrock trial raw responses and trial summary"
```
These files satisfy AIEXT-07 (reviewer can inspect each raw Bedrock response) and AIEXT-08 (reviewer can inspect expected-vs-actual comparisons).

Step 5 — If any case fails schema validation or JSON parsing:
Record the failure honestly in the raw file. Do NOT silently repair or rewrite the model output. The `parse_status` field in the comparison will show `"failed"` or `"partial"`. This is valid evidence. Note the failure in `trial_observations.md` (Task 3).
</action>

<acceptance_criteria>
- `design/output/responses/tc01_raw.json` through `tc05_raw.json` all exist and are valid JSON
- Each raw file contains `"case_id"`, `"raw_response"`, and `"metadata"` keys
- Each metadata dict contains `"model_id"`, `"region"`, `"boto3_version"`, `"prompt_sha256"`, `"input_tokens"`, `"output_tokens"` fields
- No raw response file contains a 12-digit numeric string (account ID check: `grep -P '\b\d{12}\b' design/output/responses/*.json` returns empty)
- `design/output/trial_summary.md` exists and contains a results table
- `python -m design.bedrock trial` exits 0 OR exits 1 with a clear diagnostic (non-zero exit on partial failure is acceptable evidence)
</acceptance_criteria>

### Task 3: Write the trial observations document

<read_first>
- design/output/trial_summary.md (just generated — pass/fail results per case)
- design/output/responses/tc01_raw.json through tc05_raw.json (inspect actual model outputs)
- .planning/phases/03-aws-design-bedrock-extraction-evidence/03-CONTEXT.md §D-16 (trial_observations.md content requirements: variability, failures, unsupported features, prompt improvements)
- design/cases.py (expected outputs — compare against what the model actually returned)
</read_first>

<action>
Create `design/output/trial_observations.md` — English, honest, concise (no page limit but keep focused). This is a PRIMARY evidence artifact — do not write aspirational or hypothetical content. Every observation must be grounded in what the actual trial responses show.

Required sections:

**## Trial Configuration**
- Model ID used (from metadata in any raw response file)
- Region
- Temperature and max_tokens settings
- Date of trial run

**## Case-by-Case Results**
For each of the 5 cases (tc01–tc05), one subsection with:
- The message sent
- The model's raw output text (abbreviated if long)
- Pass or fail verdict and the specific field comparison results
- Observation: what the model got right, what it missed or got wrong, any surprising behavior

**## Model Behavior Observations**
A paragraph or bullet list covering:
- Schema compliance: did the model consistently return valid JSON in the specified format?
- Field accuracy: which fields had correct vs incorrect values? Any consistent pattern in errors?
- Ambiguous case (tc04): did the model hallucinate a reason for the retry? Did it correctly use `confidence: "medium"` or `parse_status: "partial"`?
- Edge case (tc05): did the model return `{}` for parameters and `"low"` confidence, or did it fabricate parameters?
- Any output values that appear to be fabricated (not traceable to tokens in the input message)

**## Honest Assessment**
2-4 sentences stating: overall pass rate (N/5), which types of cases the model handled well, which it struggled with, and what prompt improvements would help (if any). State explicitly if any test cases produced unexpected or non-deterministic output.

**## Prompt Improvement Suggestions** (if any)
If the trial revealed ambiguities in the prompt that caused incorrect outputs, document them here with specific suggestions. If no improvements are needed, state "No prompt changes required based on observed outputs."

Write this document by reading the actual raw response files, NOT by predicting what the model will output. The content must accurately reflect what the trial produced.
</action>

<acceptance_criteria>
- `design/output/trial_observations.md` exists
- File contains a "Trial Configuration" section with the actual model_id and region
- File contains case-by-case results for all 5 cases (tc01–tc05)
- File contains explicit pass/fail verdicts for each case
- File contains an honest assessment statement with a numerical pass rate (N/5)
- File does NOT contain placeholder text like "[TBD]" or hypothetical content
- File contains at least one observation about the ambiguous case (tc04) or the edge case (tc05)
</acceptance_criteria>
