**`design/bedrock.py`**: Core Bedrock logic. Import `boto3`, `botocore.exceptions`, `os`, `sys`, `json`, `hashlib`, `datetime`, `pathlib`. Do NOT import pipeline modules directly — copy the sha256 pattern inline if needed.

Implement these functions (exact signatures from RESEARCH §9):

`def run_preflight(region: str, model_id: str) -> dict`: Validates Region and model access. Steps: (1) verify `region` is non-empty string, (2) call `boto3.client("bedrock-runtime", region_name=region)` and attempt a minimal Converse call with `messages=[{"role":"user","content":[{"text":"ping"}]}]` and `inferenceConfig={"maxTokens":1}`. Catch `NoCredentialsError` → return `{"status":"fail","check":"credentials","error_code":"NoCredentialsError","message":"No AWS credentials found in credential chain","model_id":model_id,"region":region}`. Catch `NoRegionError` → return fail dict with check="region". Catch `ClientError` with code `AccessDeniedException` → return fail dict with check="iam_permissions". Catch `ClientError` with `ResourceNotFoundException` → return fail dict with check="model_not_found". Catch `ClientError` with `ValidationException` and message containing "does not support" → return fail dict with check="converse_not_supported". On success → return `{"status":"pass","model_id":model_id,"region":region,"boto3_version":boto3.__version__,"timestamp_utc": datetime.datetime.utcnow().isoformat()+"Z"}`.

`def run_trial_case(client, model_id: str, prompt: str, max_tokens: int, temperature: float) -> dict`: Calls `client.converse(modelId=model_id, messages=[{"role":"user","content":[{"text":prompt}]}], inferenceConfig={"maxTokens":max_tokens,"temperature":temperature})`. Returns the full response dict; also records latency from `response["metrics"]["latencyMs"]` and usage from `response["usage"]`. On `ClientError` or any exception, returns `{"error": str(exc), "output": None}`.

`def validate_extraction_output(raw_text: str) -> tuple[dict | None, list[str]]`: Attempts `json.loads(raw_text)`. If parse fails, returns `(None, ["output is not valid JSON"])`. Then calls `validate_extraction(parsed)` from `design.schema`. Returns `(parsed, errors)`.

`def compare_case(case, actual: dict | None) -> dict`: Compares each field of `case.expected` against `actual`. Returns a dict: `{"case_id":case.case_id, "overall":"pass"|"fail", "field_results":[{"field":f,"expected":e,"actual":a,"match":bool},...], "validation_errors":[...]}`. `overall` is "pass" only if `actual` is not None, validation_errors is empty, and all field_results match.

`def cmd_preflight(args) -> int`: Reads `AWS_REGION` and `BEDROCK_MODEL_ID` from `os.environ`. Exits 1 with a clear message if either is unset. Calls `run_preflight(region, model_id)`. Writes result dict as JSON to `args.output` (creating parent directories). Prints result status to stdout. Returns 0 if status=="pass", 1 otherwise.

`def cmd_trial(args) -> int`: Reads env vars. Checks that a passing preflight result exists at `{args.output_dir}/preflight_result.json` with `"status":"pass"` — exits 1 with message "preflight required: run `python -m design.bedrock preflight` first" if not. Creates `{args.output_dir}/responses/` directory. Loads cases from `design.cases.CASES`. For each case: builds prompt string by combining the system instruction (from `extraction_prompt.md` role + rules) and the message. Calls `run_trial_case`. Saves raw response to `{args.output_dir}/responses/{case.case_id}_raw.json` containing: `{"case_id":..., "message":..., "raw_response":..., "metadata":{...}}` where metadata includes model_id, region, boto3_version, prompt_sha256 (SHA-256 hex of the prompt string), request_timestamp_utc, response_latency_ms, input_tokens, output_tokens, stop_reason, temperature, max_tokens. Never include credentials, session tokens, or account IDs in metadata. Calls `validate_extraction_output` on the response text, then `compare_case`. Collects all comparisons. Writes `{args.output_dir}/trial_summary.md` with a results table. Returns 0 if all cases pass, 1 otherwise.

`def cmd_report(args) -> int`: Reads saved `{args.output_dir}/responses/{case_id}_raw.json` files for tc01–tc05. Regenerates comparison from saved raw response text WITHOUT calling `boto3.client` or any AWS API. Writes `{args.output_dir}/trial_summary.md`. Deterministic: same files → same output. Returns 0.

Also create directory `design/output/` with a `.gitkeep` placeholder so the output directory exists in the repo (the `responses/` subdirectory is gitignored but the parent is not).
</action>

Create `design/extraction_prompt.md` — English, ≤2 pages (≤1400 words). Structure with these headings:

**## Role and Task**
"You are a structured log-event extraction assistant. Given a single log message string, extract the event type, related component, numeric or string parameters, your confidence in the extraction, and the parse status. Return a single JSON object with no surrounding text."

**## Input Contract**
- Input: a single `message` field value (string) extracted from a log record
- The message field may come from ERROR, WARN, or INFO log records
- Do not assume the log level — derive the event type from message content
- Process one message per request

**## Processing Rules**
Numbered list:
1. Extract only values that are explicitly present in the message string. Do not infer, assume, or fabricate field values from context, prior knowledge, or domain expertise.
2. If a field value is absent or ambiguous, use `null` for component and `{}` for parameters. Do not invent plausible values.
3. `event_type`: derive a short UPPER_SNAKE_CASE label from the message semantics (e.g., `CONNECTION_TIMEOUT`, `PAYMENT_DECLINED`, `DATA_MISMATCH`, `RETRY`, `HEARTBEAT`).
4. `component`: the named service, database, host, or subsystem the event concerns. If no component is named, use `null`.
5. `parameters`: a flat object of key-value pairs found in the message (e.g., `{"retry":"3"}`, `{"txn":"t123","code":"51"}`). Values are strings or numbers. Use `{}` if no parameters are present.
6. `confidence`: `"high"` if all fields can be extracted unambiguously; `"medium"` if interpretation was required for one or more fields; `"low"` if the message provides minimal extractable signal.
7. `parse_status`: `"success"` if all expected fields are populated; `"partial"` if one or more fields required interpretation or contain null due to absence; `"failed"` only if the message cannot be meaningfully parsed at all.
8. Return ONLY valid JSON. No markdown, no explanation, no surrounding text.

**## Output Contract**
Exact JSON schema (inline as a code block in the document):
```json
{
  "event_type": "<string>",
  "component": "<string or null>",
  "parameters": {"<key>": "<value>"},
  "confidence": "high | medium | low",
  "parse_status": "success | partial | failed"
}
```
Required fields: all five. No additional fields permitted.

**## Example Prompt and Response**
Show one concrete example using tc01:
- Input: `"ERR ConnTimeout db-primary after 30s retry=3"`
- Expected output (the exact JSON from cases.py tc01 expected dict)

**## Coverage Note**
State that the five test cases in `design/cases.py` were selected to cover: two clear ERROR patterns (tc01, tc02), one WARN-class non-ERROR message (tc03), one ambiguous retry message requiring interpretation (tc04), and one minimal edge-case message with no parameters (tc05). All six `normalize.py` ERROR patterns are within scope; WARN and INFO are explicitly included.

The evaluation method section (`## Evaluation Method for 3,000-Line Production Run`) MUST be placed at the end of this document (or alternatively in a separate `design/output/eval_method.md` — use the separate file if placing it in extraction_prompt.md would exceed the 2-page/1400-word limit). The evaluation method content:

Three tiers from CONTEXT §D-18, D-19:
1. **Schema validity** (automated): Every output must parse as valid JSON matching the schema. Target: 100%. Automated with `validate_extraction()` in `design/schema.py`.
2. **Field-level correctness** (automated against ground truth): Per-field precision/recall for `event_type` and `parameters` against ground truth derived from Phase 1's `pipeline/normalize.py` (6 ERROR patterns with known fields). Target: ≥95% for ERROR messages. Non-ERROR ground truth derived from observed message patterns in the 3,000 lines.
3. **Hallucination detection** (automated + human): Flag any output `component`, `event_type`, or parameter value not traceable to tokens present in the input message string. Target: 0% hallucination rate. Automated check: every value in the output must be a substring of the input message (modulo normalization to UPPER_SNAKE_CASE for event_type).

Sampling strategy from CONTEXT §D-19: stratified by message pattern, proportional to frequency in the 3,000 lines. Human review triggers: (a) all cases with `confidence:"low"`, (b) all cases with `parse_status:"failed"`, (c) random 5% of `confidence:"high"` results for spot-checking.

State explicitly: "This is an evaluation METHOD — it describes how to assess model performance across 3,000 lines. It does not perform 3,000 live inferences; those would require separate authorization and budget."
