Create `design/aws_daily_pipeline.md` — English, ≤1 page (≤700 words). The document must contain exactly these four sections with these headings:

**## Architecture Overview**
Describe the daily pipeline in one short paragraph referencing each service in the diagram: S3 Raw → Glue ETL (validate + transform) → S3 Curated or S3 Quarantine (dead-letter for invalid records) → Glue Data Catalog → Athena, with CloudWatch alerting on Glue job failures.

**## Service Justifications**
Bullet list, one per service:
- S3: durable, cost-effective object store for raw and curated data; natively integrates with Glue and Athena
- Glue ETL: managed Apache Spark; handles batch transform without server management; native Glue Data Catalog integration
- Glue Data Catalog: centralised metadata store; enables Athena schema-on-read without a separate Hive metastore
- Athena: serverless SQL over S3 Parquet; no cluster to manage; pay-per-query; suitable for daily reporting volume
- CloudWatch: native AWS monitoring; Glue job failure metric triggers alerts without additional tooling
- S3 Quarantine prefix: isolates invalid records (dead-letter pattern) for manual inspection without blocking valid-record flow

**## IAM Boundaries (Least Privilege)**
Three-row table: Role | Permissions | Scope.
- Ingestion Role: `s3:PutObject` | raw bucket prefix only
- Glue ETL Role: `s3:GetObject` (raw), `s3:PutObject` (curated + quarantine), `glue:*` | specific bucket ARNs
- Athena Query Role: `s3:GetObject` (curated), `s3:PutObject` (Athena results bucket), `glue:GetTable`, `glue:GetPartition` | specific table/partition ARNs

Failure handling: Glue retries on transient errors (configurable); records that fail validation are written to the quarantine prefix, not discarded; CloudWatch alarm fires on Glue job failure.

**## POC vs Conceptual Design**
Explicit table distinguishing what the local POC implements vs what this AWS design proposes:
- Log cleaning and validation: POC = Python/DuckDB local pipeline; AWS = Glue ETL job
- Storage: POC = local `data/` directory; AWS = S3 buckets
- Query/analysis: POC = DuckDB SQL; AWS = Athena
- Scheduling: POC = manual `make` command; AWS = EventBridge daily schedule (assumed)
- Monitoring: POC = none; AWS = CloudWatch alarms

**## Uncertainties and Assumptions**
Numbered list matching the four `?` annotations in the diagram:
1. Ingestion trigger: Lambda (event-driven) or EventBridge + Glue schedule (daily batch) — depends on source system capabilities
2. Network topology: Glue job may require VPC endpoint to access RDS sources; public endpoint assumed for S3
3. Athena results bucket: whether a dedicated results bucket or a separate prefix in curated bucket — cost and access-control decision
4. Data volume and cost: storage class selection (S3 Standard vs Standard-IA) depends on retention period and access frequency, which are not specified in the brief

The 6 claims to address (drawn from RESEARCH §4):

1. S3 Standard-IA as "default cheapest": S3 Standard is the default; Standard-IA has retrieval fees and 30-day minimum; "cheapest" depends on access patterns and retention. Source: AWS S3 storage class documentation (https://aws.amazon.com/s3/storage-classes/).

2. Glue reading RDS directly every 5 minutes as "standard pattern": Glue is a batch ETL service with 1-2 min cold-start; sub-hourly scheduling is impractical and expensive; direct reads add load to production RDS. For near-real-time use CDC via DMS or Kinesis; for daily batch use S3 export or DMS snapshot. Source: AWS Glue documentation on scheduling; AWS DMS documentation.

3. Parquet described as "row-based": Parquet is columnar (column-based). Columnar means values from each column are stored contiguously, enabling efficient column-selective analytical queries. This is a fundamental factual error. Source: Apache Parquet documentation (https://parquet.apache.org/docs/).

4. Lambda for 30-45 minute transforms: Lambda's maximum execution timeout is 15 minutes (900 seconds); it cannot run 30-45 minute transforms. Use Glue (Spark, no execution timeout beyond service quotas) or AWS Batch for long-running jobs. Source: AWS Lambda quotas documentation (https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html).

5. Fixed 4,000-token chunking as "always best": There is no universally optimal chunk size. The supplied reading `01_chunking_basics.md` states "Không có con số đúng cho mọi trường hợp." For structured operational documents, section-based chunking preserves semantic coherence better than fixed-size splitting. Source: `docs/onboard/datapack/reading/01_chunking_basics.md`.

6. No versioning needed for KB: Version tracking is essential for operational policy documents. This POC demonstrated the risk with the POL-01 v1/v2 conflict — without version-aware filtering, stale policy answers would be served. The supplied reading `02_rag_eval_basics.md` identifies "version trap" as a required evaluation category. Overwriting without history removes rollback capability. Source: `docs/onboard/datapack/reading/02_rag_eval_basics.md`.

After the 6 claims, add a one-sentence summary: "All six claims were verified against current AWS documentation or supplied readings; no corrections required contextual judgment without an authoritative source."
