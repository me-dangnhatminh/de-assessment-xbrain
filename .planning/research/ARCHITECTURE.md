# Architecture Patterns

**Domain:** Submission-grade Data Engineer (AI / Knowledge Engineering) assessment POC  
**Researched:** 2026-08-11  
**Confidence:** MEDIUM — architecture recommendations are grounded in the supplied assessment and current AWS official documentation; the research seam classifies the web-search provider as MEDIUM even after verification.

## Recommended Architecture

Build one small, local-first Python project with three independently runnable vertical slices, plus a clearly labelled *on-paper* AWS target. Do not make the cloud diagram a hidden dependency of the submission.

```text
Immutable supplied inputs                 Local, reproducible POC
-------------------------                 -----------------------
docs/onboard/datapack/data/ ──► pipeline/ ──► pipeline/outputs/
  app_logs_7days.jsonl       validate/clean    cleaned Parquet + quality ledger
                                                     │
                                                     └──► analysis code + recorded answers

docs/onboard/datapack/data/docs/ ──► kb/ ──► kb/outputs/
  eight operational Markdown docs   inventory/chunk/index  SQLite FTS + chunks + eval runs
                                                     │
                                                     └──► citations and version decision

five selected log messages ──► design/bedrock_trial/ ──► raw response + parsed JSON + score

All commands ──► run manifest (input hashes, config, row counts, timestamps, code revision)
```

The architectural unit is a **reproducible run**, not a notebook or a manually edited report. Each command takes immutable inputs and a checked-in configuration, writes only beneath its own output directory, and produces a machine-readable manifest. A reviewer can verify the pipeline, KB, and Bedrock trial separately, then see their summary in the root README.

### Repository Boundaries

```text
README.md                         # only entry point: setup, commands, design decisions, limits
requirements.txt / pyproject.toml # pinned local dependencies
.env.example                      # variable names only; no values or credentials
.gitignore                        # .env, caches, __pycache__, large transient runtime files

pipeline/
  run_pipeline.py                 # single local CLI: validate -> transform -> persist -> analyze
  quality_rules.py                # explicit, reviewable validation/repair rules
  analysis.py                     # four required questions, no hidden notebook state
  tests/                          # unit tests for each rule and small integration fixture
  outputs/                        # generated dataset, issue ledger, results, run manifest

kb/
  build_kb.py                     # inventory -> metadata parse -> structure-aware chunks -> SQLite FTS
  search.py                       # query, effective-version filter, cited result rendering
  metadata.py                     # document identity/version/effective-status rules
  evals/questions.yaml            # ten human-authored expected cases and pass criteria
  run_evals.py                    # retrieval and groundedness scored separately
  tests/                          # version conflict and out-of-scope cases
  outputs/                        # source inventory, chunks JSONL, kb.sqlite, evaluation evidence

design/
  aws_daily_pipeline.md + diagram # diagram and <=1-page explanation; explicitly conceptual
  bedrock_trial/                  # extraction prompt, five inputs/expected outputs, runner, evidence

sop/                              # KB update/re-index/approval SOP
AI_WORKLOG.md                     # dated, independently verified AI-use entries
```

Use `outputs/` under each feature boundary rather than one shared top-level generated-data folder. This prevents a KB rebuild from overwriting pipeline evidence and lets `.gitignore` distinguish deterministic, submission-worthy evidence (small JSON/Markdown/CSV) from reproducible bulky artifacts (Parquet, SQLite, raw Bedrock payloads if necessary). The README must say which generated files are committed as evidence and which are regenerated by command.

### Component Boundaries

| Component | Responsibility | Input contract | Output contract | Verifies |
|---|---|---|---|---|
| Pipeline reader | Read JSONL without modifying it; retain source line number and raw-line hash. | Path to original JSONL. | Parsed candidate record or parse-reject event. | Original source remains immutable. |
| Quality rules | Validate schema, timestamp, service/level values, duplicates, and repairable normalizations discovered from data. Every decision has a rule ID. | Candidate record + `quality_rules` config. | `accept`, `repair`, or `reject`; before/after values and reason. | Counts are explainable, not manually fixed. |
| Dataset writer | Persist accepted normalized records as Parquet partitioned by `event_date`; write a quality ledger and run manifest. | Accepted/repaired records and decisions. | `cleaned_logs/`, `quality_ledger.json`, `run_manifest.json`. | Row conservation: input = accepted + rejected, with duplicate policy explicit. |
| Analysis | Answer exactly the four assessment questions from the clean dataset. | Clean Parquet only. | Query code, `analysis_results.json`, readable report/table. | Results cannot accidentally include raw/rejected records. |
| KB inventory | Parse the eight document headers into a source manifest, preserving filename, document ID, version, dates, owner/approver, and supersession status. | Immutable Markdown documents. | `source_inventory.json`. | No document becomes anonymous or silently overwritten. |
| Chunk/index builder | Chunk by headings; assign deterministic chunk IDs; build local SQLite FTS index. | Inventory plus body sections. | `chunks.jsonl`, `kb.sqlite`, build manifest. | Chunk provenance and index contents are inspectable. |
| KB retrieval policy | Search active documents by default; use deterministic precedence for version conflicts; allow historical retrieval only when explicitly requested. | Query plus `as_of`/history flag. | Ranked chunks with source/section/version/effective status. | POL-01 v2 wins over v1 without deleting v1. |
| KB evaluation | Run prepared questions and report retrieval hit separately from answer groundedness. | Questions with expected source/section/version and actual cited chunks/answer. | Per-case JSON/Markdown scorecard and aggregate. | Version trap and refusal behavior are visible. |
| Bedrock trial | Invoke one configured Bedrock model for five fixed cases; validate output against schema and compare to expected output. | Prompt version, case fixture, model ID, region. | Raw response, parsed JSON, schema result, comparison, run manifest. | Model output is evidence, not a hand-copied claim. |

## Data Flow and Contracts

### 1. Local log-pipeline vertical slice

1. `python pipeline/run_pipeline.py --input docs/onboard/datapack/data/app_logs_7days.jsonl --run-id local-YYYYMMDDTHHMMSS` reads read-only input.
2. The reader records file SHA-256, source line number, and parsing result. It does not "fix" the source file.
3. `quality_rules.py` produces an append-only decision ledger. A repair preserves original and normalized values; a reject preserves a safe raw-line reference or hash, reason code, and line number.
4. The writer emits `pipeline/outputs/<run-id>/cleaned_logs/event_date=YYYY-MM-DD/*.parquet`, `quality_ledger.json`, and `run_manifest.json` atomically through a temporary run directory then rename. The analysis reads that exact run ID and emits its results alongside it.
5. Tests assert rule-level behavior, row-conservation invariants, required analysis result keys, and that source-file hashes did not change.

Parquet is appropriate for the cleaned analytic dataset because it is columnar; Athena documents compression, predicate pushdown, and parallel reads for Parquet/ORC. It is **not** described as a row-oriented, write-speed-first format. For this small POC, the primary benefit is a defensible clean-schema boundary and a cloud-compatible artifact, not performance necessity.

### 2. Local KB vertical slice

1. `python kb/build_kb.py --docs-dir docs/onboard/datapack/data/docs --run-id ...` creates a source inventory before indexing any text.
2. Metadata parsing is deliberately controlled for eight known Markdown documents: document ID from heading/filename; version, issue/effective date, owner/approver, status, supersedes/superseded-by, and source file hash. Missing metadata becomes `null` plus a validation warning—never an invented value.
3. Split at H2 sections (and preserve enclosing H1/document metadata). Split only an overlong section at paragraph boundaries with a small documented overlap. The reading pack identifies structure-based chunks as the sensible starting point for operational policies and SOPs; fixed universal token counts are not justified here.
4. Each chunk has a stable ID derived from source hash + section path + ordinal and stores `{chunk_id, document_id, source_file, section, content, version, effective_date, owner, status, source_hash}`.
5. Use SQLite FTS for transparent lexical search, paired with a Python ranking function: filter to active/effective documents first; then rank text relevance; break ties by effective date/version; return citations. This small corpus does not need an embedding service or an LLM answer generator to demonstrate searchable, attributable retrieval.
6. Encode the known backup-policy conflict explicitly: `POL-01 v2.0` is active/effective and `POL-01 v1.0` is superseded. The default search path excludes v1; a `--include-history` query can show both versions and their statuses. This retains audit provenance while ensuring the default operational answer cites v2.
7. `python kb/run_evals.py` writes each case's expected source/version, retrieved chunk IDs and ranks, answer/citations (if an answer layer is used), retrieval hit, groundedness, and pass/fail reason. At least three runs become submitted evidence; all ten fixtures remain executable.

### 3. Bedrock structured-extraction vertical slice

Keep this isolated from both deterministic pipeline cleaning and KB retrieval. It is an evaluation experiment, not a production dependency.

`design/bedrock_trial/run_cases.py` loads five immutable case fixtures, prompt text and JSON Schema by version, reads `AWS_REGION`, `BEDROCK_MODEL_ID`, and normal AWS credential-provider configuration from the environment, then calls the Bedrock Runtime API. Current Bedrock documentation supports Structured Outputs through Converse or InvokeModel for supported models. Use it when the enabled model supports it; otherwise retain the strict prompt, parse JSON locally, validate with the same JSON Schema, and report schema failures rather than repairing model text silently.

For every invocation persist: case ID, non-secret request parameters, model ID, region, prompt/schema version and hash, UTC timestamp, raw response (or a redacted response reference if policy requires), parsed object, JSON-schema validation result, expected-vs-actual field comparison, and human observation. Never let a model result alter `cleaned_logs` or the KB index.

## On-Paper AWS Daily-Pipeline Target

This is a target architecture for `design/aws_daily_pipeline.*`; it is intentionally separate from local execution.

```text
Customer daily log export
        │  (delivery/SLA to be agreed)
        ▼
S3 raw/logs/ingest_date=YYYY-MM-DD/    ← immutable, restricted write prefix
        │
        ├── daily Glue Workflow schedule (recommended for predictable daily batch)
        │     or S3/Object Created EventBridge trigger after delivery behaviour is confirmed
        ▼
Glue ETL job: validate + normalize + quality ledger
        ├── S3 quarantine/ (bad records + reason; restricted)
        ├── S3 curated/logs/event_date=YYYY-MM-DD/ (Parquet)
        └── CloudWatch logs/metrics + alarm/SNS notification
        ▼
Glue Data Catalog (explicit table schema / controlled partition update)
        ▼
Athena workgroup -> saved analysis SQL -> S3 query-results/ (separate prefix)

IAM roles and bucket/prefix policies span every arrow; human read access is distinct from workload roles.
```

**Recommended target flow:** land one daily export into a raw S3 prefix; start a Glue Workflow daily after the agreed delivery cutoff; validate/transform with a Glue job; write immutable quarantine records and partitioned Parquet curated data; update an explicitly governed Glue Catalog table/partitions; query it through an Athena workgroup. Glue supports scheduled and EventBridge-started workflows, and S3 can send Object Created events to EventBridge. For a daily batch requirement, choose the schedule first because it makes late/missing-file validation explicit; move to the event trigger only after the source-delivery contract, duplicate-event handling, and retry behavior are agreed.

**AWS responsibilities:**

| Service | Purpose in target | Explicit non-purpose |
|---|---|---|
| S3 | Separate raw, quarantine, curated, and Athena-results prefixes; retain originals. | Not the local POC's required runtime. |
| Glue Workflow/Job | Trigger controlled ETL and produce curated Parquet/quality evidence. | Not direct recurring reads from customer production databases without an approved integration design. |
| Glue Data Catalog | Persist analytic table metadata. | Not a substitute for data-quality validation or version-control of code. |
| Athena | Read-only SQL analysis over curated data, with workgroup output location and cost controls. | Not a write path for raw data. |
| EventBridge/Scheduler | Optional S3 event routing or daily orchestration with retry/DLQ design. | Not a replacement for checking that the complete daily file arrived. |
| CloudWatch + SNS | Operational logs, metrics, alarms, and notification. | Not a data-quality ledger. |
| IAM (+ KMS if selected) | Separate least-privilege workload/human access and encryption key permissions. | Not broad administrator roles shared by all components. |

Use distinct IAM roles: source delivery can write only its dated raw prefix; Glue can read raw and write only curated/quarantine and its logs; the Catalog/ETL deployer gets narrowly scoped Glue permissions; analysts get Athena query and read-only curated/catalog access; operators get logs/metrics but not raw data by default. AWS IAM and Glue documentation specifically recommend least privilege, granular customer-managed policies, and S3 access scoped to locations rather than broad console policies. Encryption choice, retention duration, VPC/private connectivity, input delivery mechanism, acceptable late-arrival window, and PII classification remain explicit customer decisions—not invented architecture facts.

## Patterns to Follow

### Pattern 1: Immutable input, append-only evidence

**What:** Treat every supplied input as read-only. Generated outputs carry `run_id`, input hash, code/version reference, configuration, counts, and timestamps.

**When:** Always, especially when a cleaning decision or AI result will be defended in an interview.

**Example run-manifest shape:**

```json
{
  "run_id": "pipeline-20260811T090000Z",
  "input": {"path": "docs/onboard/datapack/data/app_logs_7days.jsonl", "sha256": "..."},
  "rules_version": "1",
  "counts": {"read": 0, "accepted": 0, "repaired": 0, "rejected": 0},
  "outputs": ["cleaned_logs/", "quality_ledger.json", "analysis_results.json"]
}
```

### Pattern 2: Version-aware retrieval before relevance ranking

**What:** First select effective source material, then search/rank it, and always return source/version/section citations.

**When:** Operational KBs with revisions or contradictory policies.

**Why:** Relevance alone can retrieve an obsolete policy that lexically matches better. The supplied material makes `POL-01 v2` versus v1 a required correctness test.

### Pattern 3: Test fixtures as evidence contracts

**What:** Check in compact fixtures for dirty-log cases, version conflicts, out-of-scope KB questions, and five Bedrock messages. Expected outcome belongs beside the input.

**When:** At the boundary of every required claim.

**Why:** It makes regression detection and interview explanation much easier than relying on screenshots or unrepeatable interactive sessions.

## Anti-Patterns to Avoid

### One-script, one-folder submission

**What goes wrong:** A script mutates source logs, cleans, analyzes, builds an index, and writes a report in place.

**Why bad:** No reviewer can identify which input/version produced which answer, and a failed Bedrock experiment can interfere with deterministic work.

**Instead:** Use the three vertical slices and run-specific output directories above.

### Indexing documents without lifecycle metadata

**What goes wrong:** All chunks compete on text relevance; old and new backup policy content are indistinguishable.

**Why bad:** The KB can confidently cite the superseded value, violating a core requirement.

**Instead:** Inventory first, model `active/superseded` status, filter current content by default, and test the conflict.

### Treating Bedrock JSON as automatically correct

**What goes wrong:** Code accepts JSON-shaped output as fact, normalizes malformed values, or uses it to transform the production-like data path.

**Why bad:** Schema validity does not prove factual extraction; silent repair hides failures.

**Instead:** Preserve raw output, validate the schema, compare field-by-field with expected cases, and send ambiguous/unparseable messages to the defined null/unknown values or human-review outcome.

### Overbuilding AWS for a local POC

**What goes wrong:** The assessment has a cloud diagram but implementation depends on deployment, Lambda chains, managed vector databases, or direct production access.

**Why bad:** It consumes the two-day budget and reduces reproducibility. Lambda invocation timeout is capped at 15 minutes, so it is not a defensible home for stated 30–45 minute transforms.

**Instead:** Run local Python; document Glue as the target batch compute service. If Lambda appears in the diagram, restrict it to a short trigger/notification task.

## Scalability Considerations

| Concern | POC / 100 users | Later / 10K users | Not needed now |
|---|---|---|---|
| Log volume | Single local Parquet dataset and pandas/SQL analysis. | S3 date partitions, Glue ETL, Catalog, Athena; compact small files. | Spark tuning, streaming infrastructure. |
| Data delivery | Fixed local input and explicit rerun. | Delivery contract, EventBridge or schedule, idempotent run keys, retry/DLQ, late-data policy. | Direct unapproved production DB polling. |
| KB corpus | Heading chunks + SQLite FTS + human eval set. | Add governed ingestion, ACL-aware retrieval, richer ranking/embeddings only after baseline eval. | Hosted vector database or chatbot UI. |
| AI extraction | Five fixed cases, raw evidence, manual review. | Sampled evaluation on 3,000 lines, alert thresholds, model/prompt versioning. | Automated write-back into trusted datasets without review. |

## Dependency-Aware Build Order

1. **Repository contract and fixtures** — create layout, dependency lock, `.gitignore`, `.env.example`, CLI conventions, run-manifest helper, and tiny test fixtures. This enables evidence from the first useful command.
2. **Pipeline validation-to-analysis slice** — profile raw logs, encode quality rules, write clean Parquet and ledger, then implement four analysis answers and tests. The AWS design must mirror these actual stages rather than invent a different pipeline.
3. **KB inventory-to-evaluation slice** — inspect all eight docs, encode version/status metadata and structure chunks, build searchable index, then write ten evaluation fixtures and run at least three. Do this before drafting the SOP, which should describe the implemented update controls.
4. **AWS design artifact** — draw the daily target from the local pipeline boundaries; state customer decisions/uncertainties and least-privilege roles. It becomes short and credible because the local flow already exists.
5. **Bedrock prompt trial** — freeze prompt/schema and five test fixtures; run only this isolated experiment; record exact evidence and corrections. Do not block deterministic deliverables on model availability.
6. **Submission integration** — README command matrix, limitations, source citations, AI worklog entries, and clean-clone rehearsal. Confirm each required output can be regenerated independently.

## What Might Be Missing

- The source-delivery mechanism, data classification/retention requirements, AWS account/region, KMS-key policy, and acceptable late-file window are not supplied. They must stay as assumptions/uncertainties in the one-page AWS explanation.
- Whether the enabled Bedrock model supports Structured Outputs must be checked in the selected region at implementation time; the runner needs a documented fallback that still records validation failures.
- The intended answer-generation layer for the KB is unspecified. SQLite FTS plus cited retrieval is sufficient and easiest to defend; add an LLM answer layer only if there is time to evaluate it separately from retrieval.
